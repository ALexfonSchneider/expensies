# expenses

Личный анализатор расходов по PDF-выпискам банка. Загружаешь выписку,
приложение разбирает операции, запоминает их в Postgres, автоматически
раскладывает по категориям и показывает итоги по дням, неделям и месяцам,
разбивку по категориям и продавцам, тренд к предыдущему периоду.

Построено на [goplatform](../platforme): `platform.App` + `pkg/server` +
`pkg/postgres` + `pkg/observe`. Фронтенд - React + Vite + TypeScript,
собранный `dist/` встраивается в Go-бинарник, всё живёт на одном порту.

Сейчас поддерживается выписка **Яндекс Банка** ("Выписка по договору",
PDF из приложения). Парсер лежит в `internal/adapters/yandexpdf`; другой
банк - это ещё один адаптер, реализующий `domain.StatementParser`.

## Требования

- Go 1.25 (Windows).
- Docker + Compose (для Postgres) - в WSL.
- Node 18+ и npm (для сборки фронтенда) - в WSL.

## Быстрый старт

```bash
# 1. Postgres (в WSL, из каталога проекта)
docker compose up -d

# 2. Фронтенд (в WSL)
cd web && npm install && npm run build && cd ..

# 3. Сервер (Windows или WSL с Go)
go run ./cmd
```

Открыть <http://localhost:8080>, перейти в "Выписки" и загрузить PDF.
Миграции схемы применяются автоматически при старте сервера, перед тем
как HTTP начнёт принимать запросы.

Если `docker compose` в неинтерактивной WSL-сессии падает на
`docker-credential-desktop.exe`, для публичных образов достаточно
`DOCKER_CONFIG=/tmp/dockercfg-noauth docker compose up -d`, где в этом
каталоге лежит `config.json` с содержимым `{}`.

## Конфигурация

`config/config.yaml` и `config/config.postgres.yaml`, любое поле
переопределяется переменной окружения с префиксом `EXPENSES__` и `__`
между уровнями:

```
EXPENSES__SERVER__ADDR=":9090"
EXPENSES__POSTGRES__DSN="postgres://expenses:expenses@localhost:5433/expenses?sslmode=disable"
EXPENSES__OBSERVE__OTLP_ENDPOINT="localhost:4317"   # пусто = без экспорта телеметрии
EXPENSES__UPLOAD__MAX_SIZE_MB=20
EXPENSES__RECEIPTS__SYNC_INTERVAL="6h"                 # "0" выключает фоновую синхронизацию чеков
```

## Разработка фронтенда

```bash
cd web
VITE_API_TARGET=http://<ip-хоста-windows>:8080 npm run dev
```

Vite проксирует `/api` на Go-сервер. Из WSL `localhost` указывает на саму
виртуальную машину, поэтому цель проксирования задаётся явно; при
`networkingMode=mirrored` в `.wslconfig` подойдёт значение по умолчанию
`http://localhost:8080`. После правок `npm run build` и пересборка Go.

Внутри `web/node_modules` postinstall-скрипт кладёт пустой `go.mod`,
чтобы `go build ./...` не заходил в зависимости npm.

## Как устроен импорт

1. PDF читается чистой Go-библиотекой `dslipak/pdf`: текст извлекается
   постранично вместе с координатами, и каждая строка раскладывается по
   колонкам таблицы по позиции x. Заголовок таблицы проверяется на каждой
   странице - незнакомая раскладка даёт ошибку, а не тихо кривые данные.
2. Описание операции собирается из перенесённых строк, из него выводятся
   тип (`purchase`, `transfer_in`, `transfer_out`, `refund`, `cashback`),
   продавец, MCC и контрагент.
3. Суммы хранятся в копейках (`int64`). Сумма распарсенных расходов и
   приходов сверяется с итогами, напечатанными банком; расхождение
   попадает в `warnings` ответа и показывается после загрузки.
4. У каждой операции есть отпечаток (дата-время, сумма, описание,
   порядковый номер среди одинаковых). Повторная загрузка пересекающихся
   периодов не создаёт дублей: такие строки считаются и пропускаются.
   Одинаковый файл или тот же номер выписки отклоняются с 409.
5. Правила категорий применяются при импорте; "Применить ко всем
   операциям" пересчитывает всё, что не было выставлено вручную.

Сам PDF сохраняется в таблице `statements` (`file_bytes`), чтобы позже
переразобрать выписки улучшенным парсером. В нём есть персональные
данные владельца, поэтому база предназначена только для локального
использования.

Переводы между своими счетами и людям помечены категориями с флагом
`is_transfer` и по умолчанию исключены из аналитики; переключатель
"Учитывать переводы" возвращает их.

## Инструменты контроля

- **Бюджеты.** Лимит в рублях на календарный месяц для категории или на
  все расходы сразу (раздел "Категории"). Дашборд показывает полоску
  "потрачено / лимит" с маркером ожидаемого темпа на сегодня, статус
  "в плане / быстрее плана / превышен" и прогноз к концу месяца при
  текущем темпе. Плитка "Прогноз на месяц" сравнивает прогноз с общим
  лимитом. Отчёт строится по месяцу, в который попадает конец выбранного
  периода.
- **Сравнение периодов.** Таблица "сейчас / раньше / изменение" по
  категориям и продавцам против предыдущего периода той же длины,
  отсортированная по величине изменения.
- **Правило из операции.** В списке операций кнопка "Правило" открывает
  форму, заполненную продавцом (или контрагентом) этой операции; "Создать
  и применить" сразу пересчитывает автокатегории. Кнопка "Заметка"
  редактирует заметку, "Исключить" убирает операцию из всех сумм и
  графиков, оставляя её в списке.

## Чеки из «Мои чеки онлайн»

Раздел "Чеки" подключает архив электронных чеков ФНС (lkdr.nalog.ru) через
клиент `github.com/jfk9w-go/lkdr-api`. Интерактивный вход (капча и SMS)
приложение не выполняет: пользователь входит на сайт сам и вставляет в
настройки refresh token и device id из DevTools, дальше бэкенд обновляет
токены по refresh. Когда refresh token истекает, вход повторяется.

Синхронизация выполняется как задание River (очередь в Postgres через
`pkg/taskengine/river` из goplatform), адаптер `internal/adapters/riverjobs`.
Кнопка и `POST /api/v1/receipts/sync` ставят задание в очередь и сразу
возвращают статус; тело задания это `Service.RunReceiptSync`: список
чеков, позиции каждого нового, сопоставление с выпиской. Уникальность по
состоянию гарантирует одно задание в очереди или в работе; периодическое
задание с `RunOnStart` запускает его каждые `receipts.sync_interval` (по
умолчанию 6 часов, `"0"` выключает) и сразу после старта сервера, так что
прерванный прогон продолжается сам. Ошибки сети ретраятся до трёх раз,
истёкшая сессия отменяет задание до ввода нового ключа. Время следующего
запуска берётся из очереди (`GET /api/v1/receipts/sync`, поле
`next_run_at`). Схема River мигрируется тем же хуком, что и схема
приложения. Архив ограничивает клиента примерно 20 запросами в минуту,
поэтому первая загрузка длинной истории занимает время.

Сопоставление: одинаковая сумма и направление, ближайшая по времени
операция принимается в пределах 15 минут, единственный кандидат в пределах
36 часов (доставка фискализируется при вручении). Затем чеки одного
продавца, выбитые в пределах 10 минут, складываются и ищется операция на
их сумму: так доставка разбивает одну оплату на товары, доставку и
сервисный сбор. Всё остальное остаётся в списке "без операции" и
привязывается вручную из предложенных кандидатов (та же сумма, три дня в
обе стороны). Сопоставление запускается после списка чеков, в конце
синхронизации, после импорта выписки и кнопкой "Сопоставить с операциями".

В операциях появляется значок "чек" с составом покупки; на дашборде
карточка "Что покупалось чаще всего" по позициям чеков за период.

Единицы сумм в fiscal data архивом не задокументированы; адаптер
определяет рубли или копейки по сверке с итогом из списка чеков.

Архив `mco.nalog.ru` недоступен из-за пределов РФ: соединение открывается,
но ответа нет. Каждый запрос к нему ограничен 90 секундами, а
HTTP-серверу выставлен write timeout 2 минуты, чтобы такая ситуация
заканчивалась понятной ошибкой, а не зависшим запросом.

## API

Все ответы JSON, суммы в копейках, даты `YYYY-MM-DD`.

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/api/v1/statements` | multipart `file` -> импорт выписки |
| `GET` | `/api/v1/statements` | список выписок |
| `DELETE` | `/api/v1/statements/{id}` | удалить выписку с операциями |
| `GET` | `/api/v1/transactions` | `from,to,category_id,uncategorized,direction,q,include_transfers,limit,offset` |
| `PATCH` | `/api/v1/transactions/{id}` | `{"category_id": 5 \| null, "note": "...", "excluded": true}` |
| `GET/PUT` | `/api/v1/budgets`, `DELETE .../{id}` | лимиты; `PUT {"category_id": 3 \| null, "amount": 800000}` создаёт или заменяет |
| `GET` | `/api/v1/budgets/report?month=YYYY-MM` | потрачено / лимит / прогноз по каждому бюджету и итог |
| `GET` | `/api/v1/analytics/compare` | `from,to,include_transfers` -> текущий период против предыдущего по категориям и продавцам |
| `GET` | `/api/v1/analytics/items` | `from,to,limit` -> топ позиций из чеков |
| `GET/PUT/DELETE` | `/api/v1/receipts/session` | сессия архива чеков; `PUT {"phone","refresh_token","device_id"}` проверяет её одним запросом |
| `GET/POST` | `/api/v1/receipts/sync` | статус и запуск фоновой синхронизации (412 без сессии, 409 если уже идёт) |
| `GET` | `/api/v1/receipts` | `from,to,unmatched,limit,offset`; `GET .../{id}` с позициями |
| `GET` | `/api/v1/receipts/{id}/candidates` | операции той же суммы рядом по времени |
| `POST/DELETE` | `/api/v1/receipts/{id}/link` | ручная привязка `{"transaction_id"}` и отвязка |
| `POST` | `/api/v1/receipts/match` | сопоставить несопоставленные чеки с операциями |
| `GET` | `/api/v1/transactions/{id}/receipts` | чеки операции с позициями |
| `GET/POST` | `/api/v1/categories`, `PUT/DELETE .../{id}` | категории |
| `GET/POST` | `/api/v1/rules`, `DELETE .../{id}` | правила |
| `POST` | `/api/v1/rules/apply` | пересчитать автокатегории |
| `GET` | `/api/v1/analytics/summary` | `from,to,include_transfers` -> итоги, среднее в день, максимум, предыдущий период |
| `GET` | `/api/v1/analytics/series` | + `granularity=day\|week\|month` -> ряд с нулевыми корзинами |
| `GET` | `/api/v1/analytics/categories` | разбивка по категориям |
| `GET` | `/api/v1/analytics/merchants` | + `limit` -> топ продавцов |
| `GET` | `/api/v1/analytics/range` | диапазон дат с данными |
| `GET` | `/healthz/live`, `/healthz/ready` | здоровье (`ready` проверяет Postgres) |

## Тесты

```bash
make test
EXPENSES_TEST_PDF=/path/to/statement.pdf go test ./internal/adapters/yandexpdf/
```

Парсер покрыт синтетическими страницами с вымышленными данными; тест на
реальном PDF запускается только при заданной переменной и никогда не
кладёт выписку в репозиторий.

## Структура

```
cmd/main.go                        composition root (goplatform App)
internal/domain                    сущности, порты, ошибки
internal/app                       use cases: импорт, категоризация, аналитика
internal/adapters/yandexpdf        парсер PDF Яндекс Банка
internal/adapters/postgresrepo     репозитории на pgx
internal/adapters/handlers/api     JSON API (chi)
internal/adapters/handlers/spa     раздача встроенного фронтенда
internal/adapters/riverjobs        фоновые задания на River (синхронизация чеков)
migrations                         SQL-схема и сид категорий/правил (embed)
web                                React + Vite + TS, dist встраивается в бинарник
```
